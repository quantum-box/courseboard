# Course Board UI デザインルール

UI 改善（多言語化・平易化・詰め込み解消）の作業で決まったルール集。
新しい画面や文言を追加するときは、まずここに従う。

主な利用者は、ゴルフ場で日々のキャディ業務を管理するキャディマスタである。
キーボードショートカット、ドラッグ、隠れたメニューなどを知っている前提にしない。
間違いを防いで戻せること、読めて押せること、その場の表示だけで完了できることを、
表示密度より優先する。

## 1. 表示言語

3ロケール。`ja` が原文で、他は `ja` へフォールバックする。

| コード | 表示名 | 役割 |
|---|---|---|
| `ja` | 日本語 | 原文。すべてのキーはまずここに定義する |
| `ja-plain` | わかりやすい日本語 | IT・業界用語に不慣れな**大人**向けの言い換え |
| `en` | English | 英訳 |

切り替えは アカウントメニュー / ⌘K / 設定 から。選択は `localStorage`（`courseboard.locale`）に保存。

### わかりやすい日本語（ja-plain）の書き方

対象は「ITに詳しくない大人のスタッフ」。**日本語学習者や子ども向けの「やさしい日本語」ではない**。

- 漢字は普通に使う。ひらがな化・分かち書きは**しない**（かえって読みにくくなる）
- 変えるのは語彙・文の長さ・具体性:
  - カタカナIT用語・業務ジャーゴンを日常語に言い換える
    - タイムライン → 今日の予定表 / 配置 → 今日の担当決め / 月次精算 → 1か月のしめ
    - インポート → 読み込む / ステータス → 今の状態 / スタッフ紐づけ → 社員情報と結びつける
  - 一文を短く。操作は「何をどこで押すか」まで具体的に書く
  - 略語・英字は初出で補足する（CSV → 表のファイル（CSV））
- `ja` と同じ表現になるキー（「閉じる」等）は定義せず、フォールバックに任せる
- ただし**説明文（description / summary / message / body で終わるキー）は必ず書き直す**。
  `src/i18n/completeness.test.ts` が検証している

`ja-plain` だけを平易にして終わりにしない。既定の `ja` も、操作に必要な言葉は
ゴルフ場で普段使う言葉にする。「キャディ」「ラウンド」など日常のゴルフ用語は使ってよいが、
「インポート」「ステータス」「コマンドパレット」など開発者側の言葉は、
「表をとりこむ」「今の状態」「画面をさがす」のように言い換える。

開始時刻は「スタート時刻」、予約できる単位は「スタート枠」、一覧は「スタート表」と呼ぶ。
利用者向けの日本語では「ティータイム」を使わない。

### i18n 実装の約束

- ライブラリは i18next + react-i18next。初期化は `src/i18n/index.ts`（`main.tsx` で side-effect import）
- 文言は `src/i18n/locales/<locale>/<namespace>.ts` に、画面単位の namespace で置く
- `en` / `ja-plain` は `DeepPartial<typeof ja側>` で型付けし、欠けは tsc でなくテストで検出する
- namespace を増減したら `node scripts/gen-i18n-index.mjs` で各 index.ts を再生成する
- ロケールコードに大文字を含めない。i18next の正規化（`ja-EASY` 化）を避けるため
  `lowerCaseLng: true` を維持する
- コンポーネント外（バリデーション関数・エラーマップ等）は `i18next.t()`、
  コンポーネント内は `useTranslation()` を使う。言語切替に追従させるため、
  モジュール読み込み時に `t()` の結果を定数に固定しない
- API が返すコード値（`primary` / `junior` 等）は**そのまま表示しない**。
  ラベル関数で翻訳キーへマップし、未知の値のみ原文表示にフォールバックする
- デプロイ担当者しか読まない設定エラー（env 不備など）は翻訳しない

## 2. 画面構成

- **1画面1目的。** 一覧と詳細を同じ画面に横並びで押し込まない。
  一覧はテーブル、行クリックで全幅の詳細へ遷移し、「← 戻る」で一覧へ戻す
  （例: キャディ名簿 `golf/caddies` ⇄ `golf/caddies/{id}`）
- 一覧に着地したら**まず一覧を見せる**。先頭行を自動選択して詳細を開かない
- 見出しを重複させない。詳細画面では PageHeader を出さず、対象の名前を見出しにする。
  パネルのタイトルがページ見出しの繰り返しになるなら省く
- **一覧画面は PageHeader ごと省いてよい。** ワークスペースバーが画面名を出している
  ので、eyebrow・タイトル・説明文で紙面を使わず、ツールバー（検索・絞り込み・
  追加ボタンを1行）から始めて直下に表を置く（例: 社員名簿）。
  説明が要るならヘルプパネルに書く
- 毎日使う画面だけをサイドバーに置く。使用頻度の低い画面（コース設定・予約ルール・
  コースマップ）は設定ハブ配下に寄せ、⌘K からは引き続き検索できるようにする
- **設定ハブには「決めること」だけを置く。** 動作状態・連携用JSONなどの技術詳細は
  下位ページ（`settings/advanced` = システム連携の詳細）へ移す。ハブは
  リンク一覧＋日常的に触りうる設定だけにする
- **追加・編集フォームを一覧の途中に差し込まない。** 右からの Sheet
  （`src/components/Sheet.tsx`）か別ページにする。一覧の上にフォームが展開すると
  表が押し下げられ、文脈が切れる（例: プレー商品のプラン追加は Sheet）
- **編集の入口を表の上（ページ上部）に出さない。** 選択に応じて現れる操作パネルを
  ヘッダ側に置くと、行を選んだ瞬間に表全体が下へずれ、**いま選んだ行が動く**。
  選択して操作する画面（予約台帳の枠設定＝売り止め・特別料金）は Sheet に出し、
  背後の表は動かさない。表の中で選ぶ → 右で決める、の形に揃える
  （`src/features/golf/ledger/SlotMarkEditor.tsx`）
- Sheet を閉じる操作は選択の解除も兼ねる。閉じるボタンを本文側に重ねて置かない
- **画面の上に数字を並べない。** 一覧ページの先頭に指標カード（`MetricGrid`）を
  置くのは既定で禁止。数えれば分かる数（在籍◯人、キャディ◯人）は表が答えるので、
  カードは場所を取るだけで業務判断を助けない。指標を出してよいのは、その画面の
  目的そのものが数字のとき（売上目標の達成率、受けられる残り組数など）に限る
- 同じ理由で、**パネルの説明文（`description`）も既定で省く**。タイトルと表の
  見出しで意味が通るなら書かない。ページ見出しの言い換えは特に不要
- 一覧の絞り込みは**フォームではなくツールバー**にする。`Field` のラベルと
  必須／任意バッジを付けた入力欄を並べると設定画面のように見える。検索ボックスと
  セレクトを1行に並べ、ラベルは `aria-label` で持たせる
  （例: キャディ名簿・社員名簿の絞り込み）
- 1画面あたりの見出しは絞る。詰め込むより分割する
- 画面を開いた時点で、次に押す主要ボタンが1つ分かる状態にする。主要な仕事は、画面へ
  入ってから3回以内のボタン操作で開始または完了できるようにする。入力そのものは数えないが、
  入力欄を開く、次画面へ進む、確認を進める操作は数える
- 候補が決まっているコース、キャディ、日付、状態は選択式にする。管理用 ID の転記を
  求めない。自由入力は氏名、メモ、金額など候補を決められない値だけにする
- キーボードショートカット、右クリック、ホバー、ドラッグだけでしか実行できない操作を
  作らない。それらは画面上の文字付きボタンに加える補助に限る

## 3. 文言（ja 原文も含む）

- 原文の `ja` 自体も業務語で書く。内部実装の名前（Field API、extension runtime、
  テナントマスタ等）を UI に出さない
- エラーは「何が起きたか＋次に何をすればよいか」を書く。内部サービス名で説明しない
- ヘルプパネルは 1見出し2〜3文まで。「この画面ですること」と「出てくることば」の2部構成

## 4. お知らせ（成功・失敗の通知）

- 操作の結果は**トーストで出す**。`showToast()`（`src/lib/toast.ts`）を呼ぶだけでよく、
  表示先は `AppShell` に1つだけ置く
- **画面上部のバナーで知らせない。** 保存のたびに本文が押し下げられ、いま読んでいた
  行が動く。閉じるまで残り続けるのも運用の邪魔になる
- ページ内に据え置く `Notice` は、**その場に留まる状態の説明**だけに使う
  （権限がなくて操作できない、参照先が読めないので列が空になる、など）
- トーストの文言は1行で完結させる。補足が要るときだけ `title` + `message` の
  2行にする。エラーは既定より長く出る（読み直す前提）
- トーストは次に押すボタンと重なりにくい位置へ出し、通知自体に操作を持たせず、背後へ
  ポインター操作を通す。一定時間で消すことだけを重なり対策にしない
- 利用者の対応が必要な失敗は、失敗した操作の近くにも残し、「もう一度試す」を出す

## 5. コンポーネントの細部

- **仕事のために読む文字は16 CSS px未満にしない。** 本文、表、ボタン、入力欄、補足、
  エラー、凡例を含む。小さくしないと収まらない場合は、折り返す、列を省く、分ける、
  表の中だけをスクロールさせる。文章の行間は原則1.5以上
- **操作部品の反応範囲は44 × 44 CSS px以上にする。** ボタン、リンク、チェック欄、
  選択欄、押すと状態が変わる表セルが対象。小さいアイコンでも周囲の反応範囲を広げ、
  隣の反応範囲と重ねない
- `--control-height: 28px` と狭い画面の40px指定は移行前の値であり、新しい基準ではない。
  全体を一括置換せず、共通部品から別 issue で移行する。移行中も、新規または変更する
  操作部品は44pxを満たす
- 月間表など二次元の関係に意味があるデータは、文字や操作部品を縮めず、表の中だけを
  横スクロールさせる。行・列見出しを固定し、文字付きの移動ボタンを用意する。週ごとの
  別画面や独自ズームで月間の関係を失わせない
- ドロップダウン内でチェックマーク付きの選択肢を並べるときは、未選択行に
  同じ幅のスペーサー（`.menu-check-spacer`、0.875rem = アイコンと同幅）を置き、
  ラベルの左端を揃える。スペーサーには `aria-hidden="true"`
- レイアウト方式（flex ⇄ grid）を変えたら、**メディアクエリ内の旧ルールまで**掃除する。
  `.metric` の `max-width: 50%` が grid セルに残って崩れた前例あり
- 疑わしいレイアウトは推測せず、ブラウザで computed style を実測して原因を特定する

### 取り消しと削除

- 編集中の変更には、対象の近くへ文字付きの「元に戻す」ボタンを出す。`Ctrl+Z` / `⌘Z`
  は補助に限る
- 消す前に対象名と影響を確認する。「あとから戻せる」は、画面から復元できる、使用を再開
  できる、または同じ入力で同じものを作り直せて履歴・請求・参照関係を失わない、のいずれか
- 同じ時刻・内容で作り直せる手動枠などは、確認後の物理削除を認める。物理削除かどうか
  ではなく、利用者から見て取り返しがつくかで判断する
- 作り直しても業務上の情報が戻らないものは、「使用を止める」など復元可能な状態変更を使う

### 例外の記録

ルールどおりでは業務上の意味または機能を失う場合だけ例外を認める。taskdoc またはこの文書に、
対象、外れるルールと値、理由、危険を減らす代替策、見直す条件を記録する。見た目や表示密度
だけを理由にしない。部品の役割が変わった時点で例外は失効する。

最初の例外はシフト表の読み取り専用日付セルである。セルは操作部品ではないため、幅を32px、
高さを44pxとする。文字16px、固定見出し、表内横スクロール、週移動ボタンを併用する。
セルを押して編集・選択する機能を追加した時点で例外は失効し、44 × 44px以上にする。

既存違反の社内棚卸しと段階的な適用計画は公開範囲に含めません。ここに記載した
設計原則と、変更対象の画面に対するテスト・目視確認を基準にします。

## 6. 検証

- 文言変更を含む PR は `npx vitest run` を通す。
  - `src/i18n/completeness.test.ts`: en の全キー網羅 / ja にないキーの検出 /
    プレースホルダ一致 / ja-plain の説明文書き直し
- テストは `ja` 固定で走る（`src/test/setup.ts`）。文言をアサートするテストは ja の文言で書く
- UI 変更はブラウザ（`preview_start` / `npm run dev`）で3ロケールとも目視確認する
- computed style で仕事に必要な文字が16px以上、操作部品の反応範囲が44 × 44px以上で
  あることを確認する。例外は記録した値と代替策を確認する
- 200%表示で情報や操作が欠けないことを確認する。月間表は31日の月で、固定見出しと
  文字付きの移動ボタンだけでも目的の日へ到達できることを確認する
