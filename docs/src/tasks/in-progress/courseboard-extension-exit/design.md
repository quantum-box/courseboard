# 設計

## 9系統の行き先と移し方

判定基準は [ADR-0009](../../../architecture/decisions/ADR-0009-extension-config-is-not-a-data-store.md) の 2 分類。

### コース並び順 — ローカル DB、S、最初の 1 本

台帳のコース列順。文字列の配列だけで、空なら key ごと消える。読み手は台帳とティーシートの 2 つ。

行に分ける（テナント × コース × 位置）。コース ID は Field 由来の任意文字列なので、CSV に畳むと区切り文字の混入が ID の破壊になる。書き込みは差分ではなく全削除して入れ直す 1 トランザクション。順序は集合ではなく列で、部分更新の意味が定義できない。

移行は読み取り時のフォールバックで足りる。並び順は「無ければコース一覧の既定順」で画面が成立するので、移行漏れの被害が並びだけに閉じる。**フォールバックを外す瞬間だけ注意**（外した途端に既定順へ戻る）。

### ランク単価 — ローカル DB、S

4 つのランクの単価と通貨。テナントで 1 行。ランクは閉じた集合なので行ではなく列にする（ランクの増減はドメインの変更であって設定の変更ではない）。

**読み取りは 3 段のフォールバックが必須**。ローカルに行があればそれ、無ければ config、config にも無ければ既定値。現在の実装は読み取りが fail-open で既定値に落ちるため、**単純に「行が無ければ既定値」にすると、設定済みの単価が黙って戻ったまま給与計算がその金額で走る**。全テナントに行ができたことを確認してから 2 段目を外す。

0 は「そのランクの担い手がまだ居ない」として許し、負だけ拒む。現在のバリデーションと同じ判断。

### 予約ポリシーの写し — 削除、S

既定ホール数・1 組の上限人数・カート方針・預り金比率の正は Field の予約ポリシーテーブルにあり、CourseBoard は既に読み書きする経路を持っている。config 側は誰も読まない写し。

同じ場所にある公開商品名・説明・既定所要時間は**読み手が 1 つも存在しない**（Rust も desktop も、書いた本人の再表示以外に用途がない）。UI ごと消す。

シミュレータ画面の設定フォームを予約ポリシー API へ付け替えると、config への書き込み経路が 1 本消える。**着手前に、預り金比率が config と Field 側で一致しているかを 1 テナント分読んで確認する**。config 側だけ編集されて Field 側が初期値のまま、という状態がありうる。

### 料金シミュレータの前提 — ローカル DB、M

都道府県、利用税の等級、課税割合、価格弾力性、固定費、変動費。テナントで 1 行。

都道府県と等級は**ゴルフ場利用税の税率表を引く鍵**で、税率表そのものは既に CourseBoard ローカル DB にある。表と鍵が別のストアに分かれている状態を統一する。

**都道府県が未設定だと料金計算が 400 で落ちる**設計なので、既定値を推測して埋めない。空のまま計算へ進ませず画面で問う、という現在の挙動を保つ。他の 4 つは列が無かった頃のコンパイル時定数と同じ値を既定値にする。

移行は読み取り時のフォールバック。ただし**設定済みのテナントが実在する**ので、フォールバックを外す前に設定画面から再保存させて行の存在を確認する。テナント数が少ないので一括バッチは要らない。

### 表示設定 — ローカル DB、S

来場者区分の候補はゴルフ運用の語彙。日本語の自由入力なので CSV に畳まず行に分ける。行ゼロは「区分なし」で、現在の「key が無い」と同じ挙動に無害に縮退する。

既定通貨は Rust に読み手が 1 つも無く、実際に使われている通貨はランク単価のものだけ。独立した設定として残さず、ランク単価の通貨に統合する。**移行前に本番の実値を 1 度読んで確認する**。

### 外部帳票の日別集計 — ローカル DB、L、一回限りの移送が要る

3 段のネスト（コース → 日付と午前午後 → 10 フィールド）。コース数 × 日数 × 2 で行が増え続け、3 コース 1 年で 2,190 行が 1 個の JSON に入る。

**9 系統で唯一、読み取り時のフォールバックでは済まない。** 設定値ではなく履歴データで、2 つのストアの和を画面に出すと、どちらの数字が新しいかを誰も維持できない。行数も多くオペレータの再入力で埋められない。

一回限りの移送コマンドを `bin/` に足す（既存の migration ゲートと同型）。config から読んでローカルへ入れ、検証してから読み取りを切り替え、legacy を消す。dual-write はしない。**この key だけは切替後に config から明示的に削除する**（他の key と扱いを変える理由は、これだけが hot path のペイロードに乗っているから）。

過去に同じテーブルが存在し、物理移送禁止に反するとして削除された経緯がある。[ADR-0007](../../../architecture/decisions/ADR-0007-external-reservation-report-snapshots.md) にその却下理由が ADR-0009 で解かれた旨を追記済み。

### タイムゾーン — Field 起票、CourseBoard 側は M

読み手は 22 箇所（usecase 15 ファイル）で、事実上アプリ全体の前提。ただし全部が同じ port を経由しているので、差し替えは gateway 1 箇所で済む。

**CourseBoard 単独では移せない。** Field の公開ストアフロントが同じ値を読んでおり、ローカルへ移すと公開サイトのカレンダー解釈が黙って既定値に落ちる。

Field 待ちの間にできることは 2 つ。UI の耐障害化（第0波）と、Field 側の course テーブルへのミラー書き込みが既にあることの確認。

### 予約受付期間 — Field 起票、CourseBoard 側は S

「今日から N 日」と「指定日まで」の 2 形。読み手は CourseBoard の 3 箇所だけで、**厳密には今日ローカルへ置いても誰も困らない**。

それでも Field 推奨にするのは、枠生成が将来 Field の在庫生成に寄る予定で、そのとき受付期間だけ CourseBoard にあると Field が古い値で枠を作るため。

**起票が半年動かないならローカル化に切り替えてよい。** 9 系統で唯一「間違えてもロールバックが安い」（設定 1 つ、読み手 3 箇所、意味が閉じている）。

### 予約商品 — 分割する、M + Field 待ち L

この配列は Field の公開ストアフロントが商品カタログとして読んでおり、Field 側に商品テーブルが存在しない。加えて Field の枠取り込み処理が同じ配列の枠を書き換える。**CourseBoard 単独では動かせない。**

ただし要素を 2 つに割れる。

- **今すぐローカルへ出せる**（Field が読んでいないことを確認済み）: プレー種別、ホール数、対象コースの複数指定、1 組の上限人数
- **出せない**: ID、有効フラグ、予約方式、名称、所要時間、枠、販売可能リソース、そして**対象コースの単数指定**

最後の 1 つが障害になる。Field のストアフロントは、販売可能リソースが未宣言の商品にだけこれを読む。**全商品が宣言済みになれば読まれなくなる**ので、本番で 1 度数えるのが判定条件になる。

分割するときに落としてはいけないのが「宣言したかどうか」の区別。**「対象を宣言したうえで 0 件」と「未宣言」は意味が違う**（前者はどこでも売らない、後者は無制限）。現在は key の存在有無で表現しているので、テーブルでは真偽値の列にする。落とすと「どこでも売らない」商品が「どこでも売れる」商品に変わる。

分割が済むと、config に残る商品配列は**純粋に Field 所有の汎用形状**になる。Field の商品テーブルができたときの移行が汎用フィールドの引っ越しだけになり、ゴルフ語彙の交渉が消える。

## 新しい設定 API

`GET /v1/course/tenant-settings` と `PUT /v1/course/tenant-settings` を足す。

実装はローカル DB を主、config をフォールバックにする。移行の各段階で内部実装だけが変わり、**wire の契約は初日から最終形**になる。

契約で最も大事なのは、**行が 1 本も無いテナントでも 200 と既定値を返すこと**。404 も null も返さない。これがタイムゾーン Provider を throw させない条件。

書き込みは全体を受けるが、**ブラウザが持つのは自分が編集する設定だけ**。config 全体は絶対に往復させない。

extension status のレスポンスからは config を落とす。残すのは extension キー、有効状態、版番号、検証結果、更新時刻。用途が「この extension が有効か」の表示だけになり、これは lifecycle の読みなので ADR-0009 の「静的な構成値だけ」に合致する。

`PATCH /v1/course/config` は**完全に廃止する**。ルートが存在する限り、どこかの画面がまた使う。

認可は既存の予約ポリシーの action を再利用できる。定数の説明が既に「golf extension 自身の config を含む」と書いており、置き場所が config からローカル DB に変わっただけで権限の意味は変わらない。**料金前提を経理に触らせたいが予約ルールは触らせたくない、という職掌があるなら**専用の action を 1 ペア新設する。判定材料は、予約ポリシーを管理できるロールに料金前提を触ってほしい人が含まれているか。

## テナント選択の付け替え

### 処理

platform の素の `/v1/me` を呼び出し元の bearer で叩く（**スコープのヘッダは付けない**）。返ってきたテナントから platform が未設定のもの（階層の最上位）を落とし、残りを platform ごとにまとめる。まとまりごとに `POST /v1/auth/policies/check-tenants` を並行で投げ、許可されたものだけ残す。

順序は `/v1/me` の順を保つ（許可判定側の順は別物）。既定テナントは生存が正確に 1 件のときだけ立てる。platform 側の既定値はフィルタ前の集合で計算されているので、そのまま通してはいけない。

**スコープのヘッダを付けてはいけない。** 付けると、2 つ目の platform への問い合わせが「文脈と本文の platform が不一致」で 400 になる。

対象テナントは明示的に列挙する。「サーバ側で導出させる」形もあるが、導出される集合は `/v1/me` から既に持っているものと同じで、得るものがない。明示のほうが応答が決定的でテストしやすい。

### 代表 action

業務ロールが共通して持つのは 5 つ。そのうち `field_extension_golf:ListTeeSheet` を選ぶ。

- extension の概念に縛られた action は使わない。**契約を表す軸が、最も消える可能性の高い action であってはならない。**
- Field コアの action も使わない。CourseBoard を契約していないテナントのロールも持ちうるので、通してしまう。
- ティーシートが読めないテナントで CourseBoard は成立しない。「ポリシー付与＝契約」という規約の意味と、この action の意味が一致している。

machine-to-machine の税計算ロールは除外する。このエンドポイントは呼び出し元が人間のユーザーであることを要求するので、そもそも呼べない。

**この共通性をテストで固定する。** 「新しいロールを足したせいで、そのロールの人だけテナントが見えなくなった」は本番でしか気づけない種類の障害で、CI で落とすべきもの。マニフェストを読んで、代表 action が machine-to-machine を除く全ポリシーに含まれることを検査する。

### 移行

まず現行経路を寛容にする。extension ブロックの欠落を契約違反（502）ではなく「除外扱い」に落とす。**これだけで、Field が返さなくなった日に全員がサインイン不能になる事態が消える**。純粋な緩和なので即日出せて revert も自明。残りの計画がずれてもこれだけは価値がある。

次に新方式をフラグ配下に足し、比較モードを作る。両方を実行して**旧方式の結果を返し**、差分を構造化ログに出す。**本番で最低 1 営業週**（週 1 回しか触らないロールを拾う）。比較中は負け側の呼び出しをブロッキングにしない。

合格条件は「旧方式にしかないテナントがゼロ」。あれば今日動いているテナントがアクセスを失う意味なので、直し方はコードではなく**ポリシーの付与**になる。これがまさに「ポリシー付与＝契約」のオンボーディング作業そのもの。

環境ごとに切り替え、1 締め経過してから Field 呼び出しを消す。切替はフラグの変更だけでコードのデプロイが要らず、**戻すのも秒単位**。

### 縮退

`/v1/me` 自体が失敗したら 502（一覧がないので縮退先がない）。**絞り込みだけが失敗したら、絞らずに返してフラグを立てる**。

これはセキュリティホールではない。後続の全ての API が同じ Tachyon Auth に対して独立に認可し、Field も呼び出し元が関係を持たないテナントを独立に拒否する。**テナント一覧は発見の手がかりであって認可の境界ではない。**

代替（空を返す）は、障害中に全オペレータを行き止まりの画面に送る。UI にはフラグの受け口が既にあり、「少し時間をおいてもう一度」の文言も用意されている。

### 見落としやすい点

`/v1/me` のルート登録が Field の URL の有無を条件にしている。Field を消すときに条件を platform の URL 基準へ付け替えないと、テストやローカルで**ルートが黙って未登録になり 404 になる**。

UI 側は思ったより変更が少ない。テナント一覧の受け取りは既に platform ID を優先して読む形で、`platform_id` が常に入るようになるとフォールバックが発火しなくなるだけ。変えるのは「0 件かつ縮退中なら、権限がない画面ではなく再試行を促す画面へ」の 1 箇所。

権限がない画面の文言は、**新しい意味のほうがむしろ正確になる**。今までの 0 件は「どのテナントにも extension が有効化されていない」というプロビジョニングの事実で、権限の話ではなかった。何を頼めばよいかが分かる語に寄せる。

## Fieldに起票する

起票済み（2026-08-23）: 商品テーブル = PLT-3855、タイムゾーン = PLT-3856、受付期間 = PLT-3857、予約一覧の期間フィルタ = PLT-3858、小物まとめ = PLT-3859。

- **予約商品を汎用テーブルと CRUD API で持つ。** 商品が ID・有効フラグ・予約方式・名称・所要時間・販売可能リソースの許可リストを列として持ち、枠が子テーブルになること。公開ストアフロントと枠取り込みがこのテーブルを読み書きすること。**所有アプリだけが解釈する不透明な属性 JSON を 1 つ持ち、Field は検証も解釈もしない**こと（これが無いと業種固有の意味づけが config に戻る）。**「販売可能リソースを宣言したうえで対象 0 件」と「未宣言」が区別される**こと。既存 config から一方向で seed でき dual-write を必要としないこと。
- **テナントのタイムゾーンを汎用属性として持つ。** 未設定のテナントに既定値つきの 200 を返すこと。公開ストアフロントの暦の解釈がこの属性から解決され、**商品配列の存在に依存しない**こと。不正な値は保存時に拒否し、読み取り時に黙って別の値へ落とさないこと。
- **予約の受付可能期間を汎用設定として持つ。** 2 つの形を同時に持てないこと。在庫と枠生成と公開ストアフロントが参照すること。未設定は制限なしとして既存の挙動を変えないこと。
- **予約一覧に期間フィルタとページング契約を足す。** 半開区間の開始・終了とタイムゾーンを受け、応答に総数か続きの有無を含めること。**単独で最も価値が大きい**。現状は期間で絞る手段がなく、消費側は全件を件数上限で切って取るしかない。上限を超えたテナントでは期間集計もスケジュール表示も静かに不完全になり、上限に達したことを知る手段もない。
- 予約一覧の業種フィルタ、レポート期間のタイムゾーン、キャンセル料レポートの請求書 ID、期間指定の決済照合サマリ、スタッフ割当のサーバ側料率補完の廃止。

config の単一キー更新と権限分離も起票してよいが、**依存させない**。撤退が完走すれば不要になる緩和策で、先に来たら移行期間の事故率が下がるという位置づけに留める。

## Field側の実行設計（Fieldへ移す前提の覚え書き）

Field のテーブルとルートをどう汎用化するかは Field の実行設計であり、CourseBoard のリポジトリで維持すると陳腐化する。調査で判明した要点だけ残す。

- Field は `commerce_customers` → `customers` のリネームで、**旧名で始めてテーブル不在エラーのときだけ新名へ一度フォールバックし以後記憶する resolver** を実装済み。これを広げれば DB のリネームとアプリのデプロイが順序から切り離せ、「同時デプロイが必要」という制約が消える。
- 起動時のスキーマ照合に 6 つのゴルフテーブルの構造がハードコードされている。リネームと同一 commit で更新しないと CI が落ちる。このファイルは migration ではないので変更禁止の対象外。
- リネームと DROP は本番適用のゲートで destructive 判定されるので、承認行が要る。既存の DROP INDEX の理由文が手本になる。
- 汎用名の互換 VIEW が 2 つ既に存在し、リネーム先の名前と衝突する。VIEW 定義自体が列名の対応表になっている。
- Field の API バージョニング方針が `/v1/` 内での endpoint 削除を禁じており、ゴルフ移行の ADR と正面から矛盾する。extension 配下に限った例外条項を一文足すのが最も安い解。前提として、その配下の実際の呼び出し元が所有アプリだけであることをアクセスログで確認する必要がある。
- 列名のリネームはしないほうがよい。列名は wire に出ておらず、変えるとスキーマ照合・index 名・外部キー名が連鎖する。
