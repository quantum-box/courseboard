# テナント選択をポリシーで行う

親: [CourseBoardをField extensionから切り離す](../courseboard-extension-exit/task.md)。
決定は [ADR-0011](../../../architecture/decisions/ADR-0011-policy-based-tenant-selection.md)。
[/v1/me proxyとextension連動テナント選択](../../completed/v0.1.11/v1-me-proxy-extension-filter/task.md) を置き換える。

## 現状

CourseBoard の `/v1/me` は Field の `/v1/erp/me?extensionKey=golf_course` を proxy し、`tenant_extensions` で golf_course が有効なテナントだけを残している。[ADR-0010](../../../architecture/decisions/ADR-0010-courseboard-is-not-a-field-extension.md) で extension への依存をやめるとこの軸が使えなくなる。

代替は Tachyon Auth に既にある。`POST /v1/auth/policies/check-tenants` が「このユーザーがこの action を持つテナント一覧」を返し、Field 自身がこれを使っている。テナントスコープが決まる前に呼べる。

現行実装には**直しておくべきものが 2 つ**ある。

- `decode_and_filter_profile` が extension ブロックの欠落を契約違反として 502 にする。**Field が返さなくなった日に全ユーザーがサインイン不能になる。**
- `platform_id` を埋めるために Tachyon Auth へテナント数ぶん問い合わせ、先頭 20 件で打ち止めている。**21 件目以降は `platform_id` が欠け、Field のテナントチェックで拒否される。現に存在するバグ。** 素の `/v1/me` は最初から `platform_id` を返すので、この往復ごと消える。

## やること

進捗（2026-08-23）: 手順 1（寛容化）と手順 2（`COURSEBOARD_TENANT_SOURCE=compare|policy` のフラグ実装、代表 action の共通性テスト含む）は実装済み。残りは手順 0 の curl 確認、手順 3 の本番 compare 運用（1 営業週）、手順 4 の切替と Field 外し、手順 5 の UI 文言。

### 0. 着手前に確認する（実測済み・**前提が崩れた**）

2026-08-23 に compare モードを本番 platform に対して実際に走らせた結果、**このまま `policy` へ切り替えてはいけない**ことが分かった。

- `check-tenants` は Cognito ではなく CLI の**ユーザー**トークンで **200 を返す**（呼び出し元がユーザーであることの要求は満たせている）。応答も既知の項目名を含む正しい形。
- しかし同じユーザー・同じ action・同じテナントで、**単発の `check` は許可、`check-tenants` は許可テナントゼロ**と答えが食い違う。確認に使ったテナントは `tn_01kxd5gdvm9thcbj8c2e8c6yhq`、action は `field_extension_golf:ListTeeSheet`。`check` 側は同 action で守られたルート（`GET /v1/course/player-tag-options`）が 200 を返すことで確認した。
- 対象ユーザーは当該テナントの **OWNER で `customPolicyIds` は空**。つまり付与は owner 由来の暗黙のもので、**`check-tenants` はそれを数えていない**と考えられる。

design.md の「`check-tenants` は素の `check` より厳密に強い」という前提はこの実測と矛盾する。切替を進める前に、**Field / Tachyon Auth 側でどちらが正なのかを確定させる**（PLT-3860）。**この回答が出るまで第4波の切替は保留**。要求の形が誤っている可能性も完全には排除できていないが、形が誤っていれば 400 になるはずで、返ってきたのは 200 と既知の項目名だった。

なお、この食い違いを**「付与ゼロ」と誤読しない**ための修正を実装に入れた。応答が既知の項目名を1つも含まなければ、空ではなく失敗として扱い、絞らずに `partial` を立てる。契約が変わったときに全テナントが全員から消えるのが最悪の壊れ方で、それだけは避ける。

#### 元の確認事項


**Cognito の access token で `check-tenants` が通るか。** このエンドポイントは呼び出し元が人間のユーザーであることを要求する。sandbox に curl 1 本で確認できる。通らないと設計の前提が崩れるので、コードを 1 行も書く前にやる。

あわせて、本番のテナントに階層の中間レベル（platform）で運用されているものが無いかを見る。絞り込みの対象範囲の判断材料になる。

### 1. 現行経路を寛容にする（単独 PR、即日出せる）

extension ブロックの欠落と別キーを、契約違反ではなく「除外扱い」に落とす。Field が返さなくなった日に全員 502 ではなく「0 件 → 権限がない画面」になる。依然として悪いが**観測可能で復旧可能**で、何より Field 側のデプロイ順への依存が消える。

純粋な緩和なので revert も自明。**残りの計画がずれてもこれだけは価値がある。**

### 2. 新方式をフラグ配下に足す

素の `/v1/me` を叩き、platform ごとにまとめて `check-tenants` を並行で投げ、許可されたものだけ返す。**スコープのヘッダは付けない**（付けると 2 つ目の platform への問い合わせが 400 になる）。

代表 action は `field_extension_golf:ListTeeSheet`。**この action が machine-to-machine を除く全ポリシーに含まれることをテストで固定する。** 「新しいロールを足したせいでそのロールの人だけテナントが見えなくなった」は本番でしか気づけない。

### 3. 比較モードを本番で回す

両方を実行して旧方式の結果を返し、差分を構造化ログに出す。**最低 1 営業週**（週 1 回しか触らないロールを拾うため）。負け側の呼び出しをブロッキングにしない。

**合格条件は「旧方式にしかないテナントがゼロ」。** あれば今日動いているテナントがアクセスを失う意味で、直し方はコードではなくポリシーの付与になる。これが「ポリシー付与＝契約」のオンボーディング作業そのもの。

新方式にしかないテナント（ポリシーはあるが extension が付いていなかった）が多いなら、規約が既に現場と乖離している信号。

### 4. 切り替えて Field を外す

環境ごとに切り替え、1 締め経過してから Field 呼び出しとフラグを消す。切替はフラグの変更だけでコードのデプロイが要らず、戻すのも秒単位。

**`/v1/me` のルート登録が Field の URL の有無を条件にしている。** Field を消すときに platform の URL 基準へ付け替えないと、ルートが黙って未登録になり 404 になる。同じ PR で直す。

### 5. UI

変更は 1 箇所。「0 件かつ縮退中なら、権限がない画面ではなく再試行を促す画面へ」。受け口は既にある。

権限がない画面の文言は、**新しい意味のほうがむしろ正確になる**。今までの 0 件は「extension が有効化されていない」というプロビジョニングの事実で、権限の話ではなかった。何を頼めばよいかが分かる語に寄せる。

## 縮退

`/v1/me` 自体が失敗したら 502（一覧がないので縮退先がない）。**絞り込みだけが失敗したら絞らずに返してフラグを立てる。**

これはセキュリティホールではない。後続の全 API が独立に認可し、Field も独立に拒否する。テナント一覧は発見の手がかりであって認可の境界ではない。代替（空を返す）は障害中に全オペレータを行き止まりに送る。

## 完了条件

- テナント一覧が platform の `/v1/me` と `check-tenants` で組まれ、Field が経路にいない。
- 切替前に「extension が有効なテナント」と「ポリシー付与済みのテナント」の突き合わせが済み、差分がゼロである。
- 代表 action の共通性を検査するテストがある。
- `platform_id` が全テナントに入り、20 件の打ち止めが無い。
- 絞り込みに失敗したときに絞らず返し、UI がその旨を出す。
