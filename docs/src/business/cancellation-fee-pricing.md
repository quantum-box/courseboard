# キャンセル料徴収の原価と課金モデル

CourseBoard のキャンセル料徴収機能について、1件あたりの原価と課金モデルを整理する。
提案資料・価格表の根拠となる数字をここに置く。

SMS 単価は AWS の公開価格から確定済み。残る仮定は末尾の「未確定の前提」に集約した。

## 何にコストがかかるか

1件の徴収で発生するのは次のとおり。

- **通知 1通**。決済ページの URL を顧客に送る。**メールと SMS の選択制で、SMS は必須ではない**
- **決済手数料**。Stripe で決済する
- **その他**（API 呼び出し、DB 行、決済ページ表示）はほぼゼロ

リマインド再送のエンドポイントは現時点で存在しない。1件 = 1通で計算している。

### 「1件 = SMS 1通」ではない

本ドキュメントの原価は **SMS を選んだ件にのみ** 適用される。全件に SMS 原価が乗る
わけではないので、そのまま件数に掛けないこと。

- 本番の請求画面（`desktop/src/features/cancellation-fees/CancellationFeesPage.tsx`）は
  **送信チャネルをメール / SMS / 両方から選ばせる。SMS のデフォルトは off**

**メールのみで送れば通知原価はほぼゼロ**になる。ここは価格設計に直接効く。
月額プランに含める「通数」を SMS 通数で切るのか通知件数で切るのかで原価が数倍変わるため、
**プランの単位は SMS 通数で定義する**こと（下記のプラン案はすべて SMS 通数）。

### SMS の配信経路

```
CourseBoard UI → CourseBoard API → Field API → Tachyon API → AWS SNS
```

- UI は `fieldApiJson`（`desktop/src/api.ts`）で `/field-api/*` を叩き、
  これは CourseBoard API の proxy route（`src/lib.rs`、`field_proxy::proxy_field_api`）。
  ADR-0004 のとおり UI は platform API を直接叩かない
- 実際に SMS を送っているのは AWS SNS。**単価はこの経路の末端で決まる**
- `src/cancellation_fees.rs` に Twilio を直接叩く `send_sms` があるが、
  **UI からは呼ばれていない**。README がこの経路を前提に書かれているのは実態と合っていない。
  死んだコードとして整理対象

### SMS の単価（AWS 公開価格・確定値）

日本向けは **1パートあたり $0.07451**（全キャリア・全番号タイプ）。
出典は AWS End User Messaging の価格 CSV
（`End-User-Messaging-SMS-Prices.csv`。価格ページ本体は JS で読み込むため画面には出ない）。
SNS 側の配信手数料 `APN1-DeliveryAttempts-SMS` は **$0.00** で上乗せなし。

為替 158.64円/$（2026-08-10）で換算すると

- 1パート **11.8円**
- 2パート **23.6円**
- 3パート **35.5円**

### パート数の数え方

AWS の仕様（[SMS character limits](https://docs.aws.amazon.com/sms-voice/latest/userguide/sms-limitations-character.html)）。
日本語は GSM 03.38 の範囲外なので、単発は 70 文字、複数パートになると 1 パート 67 文字。
**パート数ぶん課金される。**

```
パート数 = 文字数 <= 70 ? 1 : ceil(文字数 / 67)
```

### 実際に送られている文面は133文字＝2パート

```
Course Board ゴルフです。
キャンセル料 5000JPY のお支払いをお願いします。
支払期限: 2026-07-23
https://tachyonfield.txcloud.app/pay/inv_01kxnkw0rm6xapn8tv149cnrt0
```

- 1行目 19文字 / 2行目 28文字 / 3行目 16文字 / URL 67文字 + 改行3 = **133文字**
- 2パートの上限は 134 文字なので、**余白はわずか1文字**
- 現状の単価は **23.6円/通**

**この23.6円は運任せの数字である。** 1文字でも増えると3パートに跳ねて
35.5円（+50%）になる。増える経路は複数ある。

- **キャンセル料の桁が増えると効く**。`5000JPY` が `100000JPY` になれば確実に超える
- **文面はオペレーターが編集できる**（`CancellationFeesPage.tsx` のテキストエリア）。
  一言足すだけで超える
- コース名や店舗名を足す改修が入れば確実に超える

削れる箇所は下記「実装 TODO」に挙げた。10文字前後の余裕は作れる。

なお **URL 短縮では1パートにならない**。固定部だけで66文字あり、
1パート（70文字）に収めるには URL が10文字以内でなければならず現実的でない。
URL 短縮の価値は「3パート化を防ぐバッファ稼ぎ」に限られる。

## 計算式

### 月額サブスクモデル（推奨）

回収率に左右されない。送信数だけ見ればよい。

```
月次利益 = 月額料金 − SMS通数 × SMS単価 − アカウント維持費
損益分岐の店舗数 = 自社の月額固定費 ÷ 1店舗あたり月次利益
```

### 従量課金（手数料 %）モデル

SMS は送信した全件に発生するが、決済手数料は回収できた件にしか発生しない。
払われなかった分の SMS 代を、払われた件が背負う構造になる。

```
回収1件あたりのSMS実費 = SMS単価 ÷ 回収率
原価 = SMS単価 ÷ 回収率 + 決済手数料率 × キャンセル料
粗利 = (手数料率 − 決済手数料率) × キャンセル料 − SMS単価 ÷ 回収率
損益分岐のキャンセル料 = (SMS単価 ÷ 回収率) ÷ (手数料率 − 決済手数料率)
```

決済手数料を店舗が負担する設計なら、式から `決済手数料率` の項が消える。

## 資金フローの3パターン

決済手数料を誰が負担するかは、Stripe の課金方式で決まる。
そして課金方式は資金がどの口座を通るかを決めるので、**法務の論点と直結する**。

### A. 自社の単一 Stripe アカウントで全部受ける

- 決済手数料は全額こちらの負担
- 客の支払いは一旦こちらの残高に入り、そこから店舗へ送金する
- **店舗の売上を預かる形になるため、収納代行・資金移動業の論点が発生する**

### B. Connect destination charge

- 決済はこちらのアカウント上で立つので、**決済手数料はこちら負担のまま**
- 加えて Connect アカウント維持費と店舗への送金手数料がかかる
- 資金はこちらの残高を通るので、A と同じ法務論点が残る
- **A の上位互換ではなく劣化版**。手数料を自動で抜けること以外に利点がない

### C. Connect direct charge（推奨）

- 決済が**店舗のアカウント上で直接**立つ。決済手数料は店舗の Stripe 手数料として店舗に乗る
- こちらは application fee として取り分だけ自動で抜く
- **資金がこちらの残高を通らないので、収納代行の論点が最も薄い**
- 返金・チャージバックのリスクも店舗側に乗る
- トレードオフは、店舗に Stripe アカウントを用意してもらう必要があること

以降は C を前提に数字を出す。

## 推奨する課金モデル

**決済手数料は店舗負担（実費、または 4% として 0.4% を上乗せ）＋ SMS 送信の月額サブスク。**

%課金のみのモデルと比べた優位は次のとおり。

- **収入が回収率に左右されない**。%課金モデルでは回収率が原価に直撃する
- **高単価のキャンセル料でも手数料が増えない**。%課金だと10万円のキャンセルで
  6,000円になり、店舗との交渉で揉める
- **黒字化に必要な規模が小さい**。%課金では自社固定費3万円を吸うのに
  月372件の回収が必要（下記「参考」の前提）なのに対し、月額モデルでは 4 店舗

## 月額プラン別の利益（SMS 1通 23.6円）

原価はいずれも SMS 原価 + Connect アカウント維持費300円の合計。

- 3,000円 / 20通 → 原価 773円、**利益 2,227円（74%）**
- 10,000円 / 80通 → 原価 2,191円、**利益 7,809円（78%）**
- 10,000円 / 100通 → 原価 2,664円、**利益 7,336円（73%）**
- 12,000円 / 100通 → 原価 2,664円、**利益 9,336円（78%）**

使い切らない場合はさらに良くなる。10,000円/100通のプランで月50通しか使わなければ
原価1,482円、**利益8,518円（85%）**。ただし**価格設計は使い切られた時で見ておく**。

### 3パートに跳ねた場合

文面が134文字を超えると 10,000円/100通のプランで
原価3,846円、**利益6,154円（62%）**。**1店舗あたり月1,182円、利益の16%が消える。**
100店舗なら月11.8万円。文面の文字数管理はこの規模の話になる。

### 決済手数料 4%（実費3.6%との差 0.4%）を乗せた場合

- 月100通送信・回収率60%・単価5,000円 → 回収60件 → 決済総額30万円 → 上乗せ 1,200円
- 月50通なら回収30件・決済総額15万円 → 上乗せ 600円
- 100通使い切りで **8,536円**、50通で **9,118円**
- 額としては小さいが、「決済手数料4%」と丸めて説明できる利点がある

### 超過従量

- 原価23.6円に対し **80円/通** で粗利70%
- 10,000円/100通は実質1通100円なので、それより下に置くと上位プランへ移る動機がなくなる。
  100円前後が上限の目安

## 店舗数スケール

10,000円/100通・使い切り（7,336円/店舗）で見る。

- 10店舗 → 月 73,360円
- 30店舗 → 月 220,080円
- 50店舗 → 月 366,800円
- 100店舗 → 月 733,600円

自社の月額固定費を3万円とすると、**4店舗で黒字化**。

## 参考：%課金モデルにした場合（非推奨）

決済手数料 3.6% を自社で飲む前提。回収率60%、SMS実効 39.4円（23.6 ÷ 0.6）。

- 手数料6%・キャンセル料5,000円 → 収入300円、原価219円、粗利81円
- 損益分岐のキャンセル料 = 39.4 ÷ 0.024 = **1,642円**
- 6%取っても実質の取り分は 6% − 3.6% = 2.4%。**取り分の6割が決済手数料に消える**
- 自社の月額固定費3万円を吸うのに必要な回収件数 = 30,000 ÷ 81 = **月372件**

SMS 単価が下がったことで %課金モデルの成立余地も広がったが、依然として非推奨。
粗利がキャンセル料の単価に比例するため、この試算は単価5,000円という仮定に全面的に依存する。
**回収率と単価という読めない2変数に黒字化ラインが乗ること自体が、
%課金モデルを採らない理由**になっている。

## 未確定の前提

SMS 単価は確定済み。残りは次のとおり。

- **為替 158.64円/$**（2026-08-10）。原価が直接比例するので円安が進めば上がる
- **Connect アカウント維持費 300円/店舗/月、送金手数料 0.25%**。
  Stripe の日本の料金ページで要確認。Standard アカウントなら維持費は0円
- **SMS を選ぶ比率**。メール送信なら通知原価はゼロなので、プランの通数設計に直結する。
  現在の UI は SMS が off 既定のため、実績を取るまで比率は不明
- **回収率 60%**。%課金モデルの試算にのみ影響する。実績が出たら差し替え
- **自社の月額固定費 3万円**。サーバ・DB の実績値で差し替え

%課金モデルの試算はこれに加えて **キャンセル料の平均単価 5,000円** を仮定している。

AWS は「価格は頻繁に変わる、正確な額は利用レポートで確認」と明記しているため、
**実際の請求書が出たら $0.07451 と突き合わせること。**

営業・契約面で決める必要があるもの。

- 店舗の Stripe アカウントを Standard（店舗が自分で契約）にするか、
  Express（こちらが代理で作成）にするか。導入の容易さと維持費のトレードオフ
- 店舗から見ると「決済手数料3.6%は自分持ち＋月額料金」になる。
  「決済手数料は実費、システム利用料は月額」と分けて説明する形にする
- 収納代行の論点は direct charge で薄くなるが、最終的な判断は専門家に確認する
