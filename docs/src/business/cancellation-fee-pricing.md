# キャンセル料徴収の原価と課金モデル

CourseBoard のキャンセル料徴収機能について、1件あたりの原価と課金モデルを整理する。
提案資料・価格表の根拠となる数字をここに置く。

金額の前提は末尾の「未確定の前提」に集約した。レートが変わったらそこだけ差し替える。

## 何にコストがかかるか

実装上、1件の徴収で発生するのは次のとおり（`src/cancellation_fees.rs`）。

- **SMS 1通**。Field invoice を作成し、公開 payment URL を SMS で送る
- **決済手数料**。Stripe で決済する。publishable key は Field invoice 側から取得している
- **その他**（Field API 呼び出し、DB 行、決済ページ表示）はほぼゼロ

リマインド再送のエンドポイントは現時点で存在しない。1件 = 1通で計算している。

### SMS のパート数

日本語（漢字・絵文字を含む）の SMS は 1 パート 70 文字。71 文字以上になると
1 パートあたり 67 文字に減る。

```
パート数 = 文字数 <= 70 ? 1 : ceil(文字数 / 67)
```

現在のデフォルトテンプレート（`render_sms_message`）は **172 文字 = 3 パート**。
内訳で効いているのは payment URL の **87 文字**で、
`{public_ui_base_url}#/pay/{32文字トークン}` という構成になっている（`CancellationFeeConfig::payment_url`）。

作業前提として **1通 57円**（3パート）で計算する。
URL を 40 文字程度まで短縮すれば 2 パートに収まり、**1通 38円**まで下がる。

## 計算式

### 従量課金（手数料 %）モデルの場合

SMS は送信した全件に発生するが、決済手数料は回収できた件にしか発生しない。
払われなかった分の SMS 代を、払われた件が背負う構造になる。

```
回収1件あたりのSMS実費 = SMS単価 ÷ 回収率
原価 = SMS単価 ÷ 回収率 + 決済手数料率 × キャンセル料
粗利 = (手数料率 − 決済手数料率) × キャンセル料 − SMS単価 ÷ 回収率
損益分岐のキャンセル料 = (SMS単価 ÷ 回収率) ÷ (手数料率 − 決済手数料率)
```

決済手数料を店舗が負担する設計なら、式から `決済手数料率` の項が消える。

### 月額サブスクモデルの場合

回収率に左右されない。送信数だけ見ればよい。

```
月次利益 = 月額料金 − 送信数 × SMS単価 − アカウント維持費
損益分岐の店舗数 = 自社の月額固定費 ÷ 1店舗あたり月次利益
```

## 資金フローの3パターン

決済手数料を誰が負担するかは、Stripe の課金方式で決まる。
そして課金方式は資金がどの口座を通るかを決めるので、**法務の論点と直結する**。

### A. 自社の単一 Stripe アカウントで全部受ける

- 決済手数料は全額こちらの負担
- 客の支払いは一旦こちらの残高に入り、そこから店舗へ送金する
- **店舗の売上を預かる形になるため、収納代行・資金移動業の論点が発生する**

### B. Connect destination charge

- 決済はこちらのアカウント上で立つので、**決済手数料はこちら負担のまま**
- 加えて Connect アカウント維持費と店舗への送金手数料がかかる
- 資金はこちらの残高を通るので、A と同じ法務論点が残る
- **A の上位互換ではなく劣化版**。手数料を自動で抜けること以外に利点がない

### C. Connect direct charge（推奨）

- 決済が**店舗のアカウント上で直接**立つ。決済手数料は店舗の Stripe 手数料として店舗に乗る
- こちらは application fee として取り分だけ自動で抜く
- **資金がこちらの残高を通らないので、収納代行の論点が最も薄い**
- 返金・チャージバックのリスクも店舗側に乗る
- トレードオフは、店舗に Stripe アカウントを用意してもらう必要があること

以降は C を前提に数字を出す。

## 推奨する課金モデル

**決済手数料は店舗負担（実費、または 4% として 0.4% を上乗せ）＋ SMS 送信の月額サブスク。**

%課金のみのモデルと比べた優位は次のとおり。

- **収入が回収率に左右されない**。%課金モデルでは回収率が原価に直撃し、
  回収率 60% だと SMS 実費が 1.67 倍に膨らむ
- **高単価のキャンセル料でも手数料が増えない**。%課金だと10万円のキャンセルで
  6,000円になり、店舗との交渉で揉める
- **黒字化に必要な規模が小さい**。%課金では月159件の回収が必要だったのに対し、
  月額モデルでは 6〜8 店舗

## 月額プラン別の利益（SMS 1通 57円）

### 10,000円 / 100通込み

- 収入 10,000円
- SMS 100 × 57 = 5,700円
- Connect アカウント維持費 300円
- **利益 4,000円、利益率 40%**

100通込みで1万円は、実質 **1通100円で売っている**のと同じ。原価57円なので粗利43%。
SaaS としては薄い。

### 使い切らない場合

- 月50通 → 原価 2,850円、**利益 6,850円（69%）**
- 実際には使い切る店舗のほうが少ないので平均はこの辺に落ちるが、
  **価格設計は使い切られた時で見ておく**

### URL 短縮後（1通 38円）

- 100通で原価 3,800円 → **利益 5,900円（59%）**
- 利益が約1.5倍になる

### 決済手数料 4%（実費3.6%との差 0.4%）を乗せた場合

- 月100件送信・回収率60%・単価5,000円 → 決済総額30万円 → 上乗せ 1,200円
- 100通使い切りで **5,200円**、50通で **8,050円**
- 額としては小さいが、「決済手数料4%」と丸めて説明できる利点がある

### プラン構成の案

10,000円/100通は原価率57%でギリギリすぎる。通数を絞るか価格を上げる。

- 3,000円 / 20通 → 原価 1,140円、**利益 1,860円（62%）**
- 10,000円 / 80通 → 原価 4,560円、**利益 5,140円（51%）**
- 12,000円 / 100通 → 原価 5,700円、**利益 6,000円（50%）**
- 超過従量 **150円/通** → 粗利62%。込み分の実質単価100円より高く設定し、
  上位プランへの移行を促す

## 店舗数スケール

100通使い切り・URL短縮なしの保守的な数字（4,000円/店舗）で見る。

- 10店舗 → 月 40,000円
- 30店舗 → 月 120,000円
- 50店舗 → 月 200,000円
- 100店舗 → 月 400,000円

自社の月額固定費を3万円とすると、**8店舗で黒字化**。URL短縮後なら6店舗。

## 参考：%課金モデルにした場合（非推奨）

決済手数料 3.6% を自社で飲む前提。回収率60%、SMS実効 95円（57 ÷ 0.6）。

- 手数料6%・キャンセル料5,000円 → 収入300円、原価275円、粗利25円
- 損益分岐のキャンセル料 = 95 ÷ 0.024 = **3,958円**
- 6%取っても実質の取り分は 6% − 3.6% = 2.4%。**取り分の6割が決済手数料に消える**
- 低単価案件で赤字になるため、%課金を採る場合は
  「6% または最低500円の高い方」のような下限設定が必須

   1通 57円 → 38円。10,000円/100通のプランで **1店舗あたり月1,900円の利益改善**。

   テナントごとの送信数カウントと超過検知が要る
4. **リマインド再送**。現在エンドポイントがない。入れると SMS 原価が倍になる一方で

## 未確定の前提

数字が変わったらここを差し替える。下流の計算は全部この4つで決まる。

- **SMS 単価 57円**（3パート想定）。AWS SNS の日本向け現行レートで要確認
- **Connect アカウント維持費 300円/店舗/月、送金手数料 0.25%**。
  Stripe の日本の料金ページで要確認。Standard アカウントなら維持費は0円
- **回収率 60%**。%課金モデルの試算にのみ影響する。実績が出たら差し替え
- **自社の月額固定費 3万円**。サーバ・DB の実績値で差し替え

営業・契約面で決める必要があるもの。

- 店舗の Stripe アカウントを Standard（店舗が自分で契約）にするか、
  Express（こちらが代理で作成）にするか。導入の容易さと維持費のトレードオフ
- 店舗から見ると「決済手数料3.6%は自分持ち＋月額料金」になる。
  「決済手数料は実費、システム利用料は月額」と分けて説明する形にする
- 収納代行の論点は direct charge で薄くなるが、最終的な判断は専門家に確認する
